● Looking at what's actually in your docs vs. the competitive landscape, the
  unique surface area isn't "another coding agent" — it's that Codebolt is a
  platform for building, orchestrating, and shipping multiple agents, not a
  single agent itself. That's the wedge.

  Recommended positioning

  ▎ Codebolt — the Agentic IDE.
  ▎ Where one developer ships a team of agents.

  Or in the same form factor as your peer examples:

  ┌─────────────┬──────────────────────────────────┐
  │   Product   │           Positioning            │
  ├─────────────┼──────────────────────────────────┤
  │ Claude Code │ Coding assistant                 │
  ├─────────────┼──────────────────────────────────┤
  │ Pi          │ Easily-integrated small agent    │
  ├─────────────┼──────────────────────────────────┤
  │ OpenClaw    │ Always-on personal agent         │
  ├─────────────┼──────────────────────────────────┤
  │ Codebolt    │ Multi-agent IDE / Agent platform │
  └─────────────┴──────────────────────────────────┘

  Why this is defensible

  Every single-agent tool (Claude Code, Cursor, Cline, Aider) collapses to "AI
  pair programmer." Devin/Codex/Jules collapse to "autonomous SWE." None of them
   position around the things your docs actually spend pages on:

  1. Multi-agent coordination is first-class, not bolted on — Swarms, Jobs,
  Mail/Inbox, Deliberation, Orchestrators. No competitor has this surface.
  2. You build agents, you don't just use one — Marketplace publishing for
  agents, skills, plugins, MCPs, capabilities, executors, providers, action
  blocks. Codebolt is a platform, peers are products.
  3. Eval + Optimization loop is built in — measure → auto-improve. This is
  infra most teams hand-roll.
  4. Three runtime surfaces, one product — Local desktop, Cloud sandboxes,
  Self-hosted. Cursor is local-only, Devin is cloud-only.
  5. Planning lives in the repo — Specs, Roadmap, Tasks, Action Plans as plain
  files. Linear-meets-IDE that other tools just don't touch.
  6. Agents ship to external surfaces — Telegram/Slack/Discord/Teams via Routing
   Gateway. Your agents leave the IDE.

  Three positioning candidates to choose from

  A. "The Agentic IDE" — clean, parallels "the AI IDE" framing of Cursor, but
  the agentic word signals multi-agent + orchestration.
  Risk: "IDE" undersells the cloud + marketplace pieces.

  B. "The platform for shipping agentic software" — emphasizes build → publish →
   run lifecycle. Differentiates from "agent that codes for you."
  Risk: "platform" is fuzzy; harder to grok in 3 seconds.

  C. "One developer. A team of agents." — outcome-oriented, evocative. Paired
  tagline with a category label like Agentic Workbench or Multi-Agent IDE.
  Risk: poetic, less crisp on the what.

  My pick

  Category: Agentic IDE (or Multi-Agent IDE if you want to be even more
  pointed).
  Tagline: Build, orchestrate, and ship agents — from one workbench.

  This forces the comparison onto your home turf. Claude Code can't credibly
  claim it; Cursor can't either; Devin definitely can't. And it maps cleanly
  onto your existing doc structure — Build on Codebolt, Multi-Agent
  Coordination, Cloud, Marketplace are all evidence for the claim.

  The one thing I'd refine over time: pick whether the hero noun is "agents"
  (you build them) or "agentic apps" (you build products powered by them). Your
  Custom Agentic Applications section suggests the latter is where the real
  wedge is — and "the IDE for agentic apps" is a category nobody owns yet.

● Yes — strong call, and it's the architectural decision that makes the engine 
  positioning honest instead of marketing fluff. If "Codebolt is the engine for

  Why this is the right separation

  It's already true. Reading your docs: the CLI runs a server on port 3100, the
  desktop app connects to it, the cloud spins up a sandbox running the same
  server, the cloud plugin tunnels a local server to a browser client. The
  engine/client split exists in the code — you'd just be making it visible in
  the product surface.

  It matches the dev-first vibe we locked in. Every dev-respected infrastructure
   brand is shaped this way:

  ┌──────────┬───────────────┬───────────────┬──────────────────────────────┐

  │          │ server        │               │                              │

  ├──────────┼───────────────┼───────────────┼──────────────────────────────┤

  └──────────┴───────────────┴───────────────┴──────────────────────────────┘

  This is a pattern devs read instantly. It's also what makes the Custom Agentic
   Applications story credible — if the engine is independently installable,
  then "build your own UI on top" is a real feature, not a bullet on a slide.

  The cleanest naming structure

  Codebolt                    ← the brand, = the Engine
  ├── Codebolt Engine         ← the runtime. Headless. Open to any client.
  ├── Codebolt Editor         ← the polished desktop IDE. One client.
  ├── Codebolt CLI            ← terminal client.
  ├── Codebolt TUI            ← in-terminal full UI.
  ├── Codebolt Cloud          ← hosted engine + portal browser client.
  └── Codebolt SDK            ← embed the engine in your own product.

  Two specific calls inside this structure:

  1. The brand Codebolt should equal the Engine, not the Editor. When someone
  says "I use Codebolt," that should mean "I use the engine — through some
  client." Same way "I use Postgres" doesn't mean "I use psql." The Editor is
  one of several clients of Codebolt.
  2. Codebolt Engine over Codebolt Server. "Server" is more accurate but
  generic; "Engine" carries the brand promise we just locked. Stripe doesn't say
   "Stripe Server" — they say "Stripe." Adopt the same: the engine is just
  Codebolt, and Codebolt Engine is its full name when you need to disambiguate
  from the Editor.

  What this unlocks

  - Honest multi-surface story. The CLI, Editor, and Cloud aren't competing
  surfaces — they're peers. The headline "CLI · IDE · platform" finally has
  architectural weight behind it.
  - Self-host as a real product. "Run the engine on your infra, connect any
  client" — that's a sentence enterprises pay for. It's also what your
  self-hosted agents docs are already pointing at.
  - Custom apps become first-class. A customer building their own UI on top of
  the engine isn't a footnote — they're using the same architecture as your own
  Editor, just with a different front-end. That's exactly the moldable/platform
  dimension we discussed.
  - CI / headless / agent-only deployments. The engine alone, no UI, running
  unattended on a server. This is a major use case (autonomous agents, scheduled
   runs, webhook responders) and it requires the engine to stand alone.
  - Cleaner pricing surface, if you ever need one. Editor free, engine free,
  marketplace + cloud + self-host = the commercial layer. Standard infra-product
   shape.

  The trade-offs to be deliberate about

  1. Onboarding friction. Two things to install. Solve this with codebolt (the
  CLI) bundling both: codebolt install pulls the engine + Editor; codebolt serve
   runs just the engine. Most users never feel the split.
  2. Version compatibility. Engine and Editor will drift. Either pin them
  tightly (Editor ships with a known engine version) or build a compatibility
  matrix into the Editor's first-run check. Postgres/Docker both solved this —
  pick a model.
  3. The marketing site needs hierarchy. Don't list six products on the
  homepage. Lead with Codebolt (the engine). Sub-pages or nav reveal "How to use
   it: Editor / CLI / Cloud / SDK." One brand, surfaced through clients.
  4. "Where do I download Codebolt" must have an obvious answer. That answer
  should be the Editor for most users, with a clear "or just want the engine?"
  path one click away. Same answer Docker gives: Desktop is the default, daemon
  is the truth underneath.
